# 贡献指南

## 可以贡献什么

1. **示例课**：按五段式模板写一篇新题型的课，过 `check_lesson.py` 全项。
2. **新模块**：按 SKILL.md 3.1 的六字段声明，附第一篇 B 层课文。
3. **失效案例**：讲法没起作用的原始对话（脱敏），比成功案例更有价值。
4. **工具**：校验脚本的检查项扩展、CI 改进。

## 提交新模块

模块不是"又一类题"，而是"一种可迁移的认知状态"。提交前先自查：

- 目标题类是否落入现有模块的问题表述模式？落入就扩展边界参数，不新建。
- 能否写出"不覆盖的问题"字段？写不出说明边界还没想清，暂缓。
- 核心动词是否比题解术语更根本？（例："该去哪"比"置换环"更根本）

PR 里需要包含：

1. `docs/modules.md` 的索引行；
2. 六字段声明（写入 SKILL.md 第 3 章或独立模块文件）；
3. 一篇 B 层课文，放在 `examples/`；
4. `check_lesson.py` 的通过记录（贴输出）。

## 写作红线

- 不出现评价型元问题：`你理解了吗`、`你觉得难吗`、`你确定吗`。
- 不出现诊断宣告：`你可能缺少`、`你还没掌握`。
- 抽象术语的首现必须晚于第一个具体过程。
- 并置案例只允许一处参数差异，且该参数在模块的边界参数清单内。
- 允许读者错过，不追加"确保理解"的追问。

完整清单见 SKILL.md 5.1，脚本实现了其中可机器判定的部分。

## 本地验证

```bash
python -m unittest discover -s tests -v

python skills/algo-implicit-heuristics/scripts/check_lesson.py \
  tests/fixtures/good_lesson.txt \
  --terms "连续段" --verbs "留下" --entity "[1, 1, 2]"
```

第二条命令退出码应为 0。对反例 fixture 运行时应为 1。

## PR 检查表

- [ ] 新增/修改的课文跑过清单，输出贴在 PR 描述里
- [ ] 若是模块变更，六字段齐全，且索引同步更新
- [ ] CHANGELOG 已更新
- [ ] 没有引入对特定平台、模型或工具链的依赖

## 讨论方式

开 issue 时贴原始对话和当时的请求，不要只贴结论。"这段讲得不好"无法定位；"这两段并置之后我没有任何疑问"可以。
