# 路线图：从 alpha 到可发布

判断标准只有一条：**别人拿到仓库，能不能在不问你任何问题的情况下用起来，并且知道它什么时候不该用。**

当前版本能装、能跑、有示例，但模块库只有两个实例，没有任何实证。下面按依赖顺序排，不按日历排。

## Phase 0 · 仓库化（本次完成）

- [x] 目录结构、README、LICENSE（MIT）、CHANGELOG
- [x] SKILL.md 与 check_lesson.py 入库
- [x] 两篇示例课
- [x] 校验脚本的正例/反例测试与 CI
- [x] 设计说明与路线图

**验收**：`python -m unittest discover tests` 全绿；CI 在 Linux 上跑通；README 里的命令逐条可复制执行。

## Phase 1 · 内容完备（决定能不能被别人用）

### 1.1 模块库

现在只有模块 A、B。开源之后，用户遇到的多数题会落到 3.2 的"现场声明"路径——这对执行者的要求偏高。

- [ ] 把"删除元素 + 保序 + 相邻约束"整理为模块 C，补齐六字段声明与一篇 B 层课文（素材已在对话中验证过）
- [ ] 再补 2–3 个高频题族：二分边界、双指针去重、前缀和/差分
- [ ] `docs/modules.md`：模块索引表（问题表述模式 → 模块 → 示例课），供路由直接查
- [ ] 每个模块配一个"不覆盖的问题"清单，防止硬套

**验收**：随机抽 10 道中等难度题，至少 6 道能路由到现有模块，而不是现场声明。

### 1.2 示例课

- [ ] 每模块至少一篇完整 B 层课文，格式统一（题目、层级、课文、执行标注、校验结果）
- [ ] 补一篇 A 层与一篇 C 层的对照，展示层级差异长什么样
- [ ] 反例课：一篇故意违反 5.1 的课文，标明问题点（教学与测试两用）

**验收**：示例课全部通过 `check_lesson.py`；反例课稳定失败并给出预期原因。

### 1.3 英文版

GitHub 的主要受众不读中文。

- [ ] `SKILL.en.md`：全文翻译，术语表统一（implicit heuristics / calibration error / run / parallel cases）
- [ ] README 英文段扩写为一节，说明与中文版的版本对应关系
- [ ] 明确维护策略：中文为源，英文滞后一个版本，CHANGELOG 标注

**验收**：英文版通过同一套 5.1 检查（正则需要英文变体）。

## Phase 2 · 工程化（决定别人敢不敢贡献）

- [ ] `check_lesson.py` 扩展第 7 项：并置案例的"恰好一项差异"可半自动核对（需要案例的结构化标注）
- [ ] `scripts/check_skill.py`：校验 SKILL.md 结构（章节齐全、交叉引用无悬空、模块声明六字段完整）
- [ ] CI 增加：SKILL.md 结构校验、示例课全量跑清单
- [ ] 发布前检查清单（`docs/release-checklist.md`）

**验收**：新增一个模块时，CI 能自动指出缺了哪个字段、哪篇示例课未通过。

## Phase 3 · 证据（决定别人信不信）

这是最容易被质疑、也最容易糊弄的一块。不做对照实验，至少要有可复核的个案数据。

- [ ] 评分 rubric：5 条以内，人工可打（是否出现显性提问、术语是否晚于过程、是否给出可迁移的表述、边界是否以案例出现、是否有可执行的下一步）
- [ ] 小样本使用记录：5–10 人，每人 2–3 道题，记录原始对话与 rubric 评分
- [ ] 失败案例集：至少 5 个"这套讲法没起作用"的案例，写清失效环节
- [ ] 数据与结论放在 `docs/evidence.md`，原始材料放 `evidence/`，匿名化

**验收**：README 的"诚实声明"一节能指向具体数据，而不是一句"尚未验证"。

## Phase 4 · 发布

- [ ] 版本 tag：v0.1.0（当前）→ v1.0.0 的准入条件写进 release checklist
- [ ] Issue 模板：`bug`（讲法失效）、`module-proposal`（新模块）、`evidence`（使用记录）
- [ ] 发布渠道：V2EX、知乎、Reddit r/leetcode、Hacker News（按受众调整文案）
- [ ] 收集前两周 issue，决定 v1.0 是否延期

**v1.0 准入条件（建议）**：模块库 ≥ 5 个；示例课 ≥ 6 篇且全部过清单；英文版可用；至少 10 份可复核的使用记录；无未处理的 P0 问题。

## 持续事项

- **模块准入**：新模块必须走 3.1 的六字段声明 + 第一篇课文过 5.1，缺一不收。
- **清单只增不减**：删除检查项需要在 PR 里写明理由。
- **版本节奏**：内容修订走 patch，模块新增走 minor，结构调整走 major。

## 不建议做的事

- 不做题库：题目映射表只记"题型 → 模块"，不存题解。
- 不做"提分"承诺：现有证据支撑不了，写进 README 只会透支信任。
- 不追求覆盖所有题：这套方法的强项是概念形成，不是实现训练。把不适用的场景写清楚，比强行扩表更有价值。
