# 第 7 讲 · Count the Cost：把评估的眼光转向成本

> 官方英文标题：**Count the Cost**　｜　斯坦福 CS193T（2026 秋）
> 课程页：https://web.stanford.edu/class/archive/cs/cs193t/cs193t.1272/lectures/07-budget/
> 视频：https://www.youtube.com/watch?v=I7zvCSGMkoc　｜　幻灯片：`../slides/07-budget.pdf`

### 这一讲在解决什么
第 6 讲教你怎么正式评估一个 AI 系统（ground truth、benchmark、LLM-as-judge）。第 7 讲用同一双眼睛看**成本**。

### 官方描述（译）
先做具体的事：逐行读一份真实的 Claude Code 用量报告，看缓存到底怎么省钱 ——
它复用的正是第 1 讲讲过的注意力机制的计算。然后看 AI 的用电和用水估算，以及它们怎么随任务类型和上下文大小变化。
接着讲模型选择：**更大不一定更好**，尤其是在多步 agent 工作流里，延迟会叠加。
再到 API key：它是什么、为什么对计费和安防都关键，并现场演示它到底是怎么泄露的。
最后是一件时事：AI 的真实成本怎么成了 2026 年美国中期选举里的一个重要议题。

### 关键概念
- **token 就是钱**：输入、输出、缓存命中率，三个数决定账单
- **缓存省钱的原理**：相同的上下文前缀不用重算 —— 所以"把稳定的部分放前面"是有经济含义的
- **延迟会叠加**：agent 跑 10 步，每步慢 2 秒，用户体验就是慢 20 秒。所以小模型在流水线里常常更优
- **水与电**：AI 的环境成本不是玄学，有可估算的量级，而且和你的上下文长度直接相关
- **API key 泄露**：最常见的方式不是被黑，是**被提交进代码仓库**、贴进聊天、写进前端

### 看的时候留意
1. 那份用量报告的逐行解读 —— 这是全课最"可操作"的一段，建议暂停对着自己的账单看一遍
2. "更大不一定更好"的适用边界：什么时候值得用大模型，什么时候是浪费
3. key 泄露演示：看完去搜一遍你自己的仓库历史

### 自测
1. 你最近一周的 AI 用量，钱主要花在哪一类操作上？哪一类其实可以换更小的模型？
2. 什么情况下缓存会失效？你怎么组织上下文能让命中率更高？
3. 说出三种 API key 泄露路径，以及你各自的防线。
