# 表达式求值函数拆解

# 程序拆解分析

先说明一点：题目要求"算符优先算法"，而本实现用的是**递归下降解析**。两者在表达式的优先级和结合性处理上是**等价**的——算符优先用栈 + 优先级表，递归下降用"分层函数"隐式编码了同一张优先级表。下面分别从两个角度拆解。

***

## 一、算法设计逻辑

### 1. 优先级"分层"——用函数调用栈取代算符栈

算符优先算法的本质是把优先级表化成"栈顶与当前算符比较"。递归下降把它改写成**优先级由低到高的分层函数链**：

```
parseExpression  ← 只处理 + -     (优先级 1，最低)
   └ parseTerm   ← 只处理 * / %   (优先级 2)
        └ parseUnary ← 处理一元 -  (优先级 3)
             └ parsePower ← 处理 ^ (优先级 4，最高)
                  └ parsePrimary ← 原子：数字、( 表达式 )
```

**调用关系本身就是优先级**：高优先级函数在低优先级函数内部被调用，所以"先算乘除后算加减"由函数调用顺序保证，不需要显式优先级表。

### 2. 左结合 vs 右结合——循环 vs 递归的分界

这是本实现最关键的设计选择：

| **运算**      | **结合性** | **实现方式**     | **位置**                          |
| ----------- | ------- | ------------ | ------------------------------- |
| `+ - * / %` | 左结合     | `while` 循环累积 | `parseTerm` / `parseExpression` |
| `^`         | **右结合** | 递归调用自身       | `parsePower`                    |
| 一元 `-`      | 右结合（前缀） | 递归调用自身       | `parseUnary`                    |

**为什么左结合用循环？** 如 `10-20/4`，`parseExpression` 中 `v=10`，循环里不断把 `- parseTerm()` 的结果扣到 `v` 上，自然左结合。循环每轮右边只调用更高优先级函数，保证不会错误跨界。

**为什么右结合必须用递归？** `2^3^2 = 2^(3^2) = 512`。在 `parsePower` 里算完左边 base 后，遇到 `^` **立即递归 parseUnary()** 拿右边，右边再自己递归处理下一个 `^`，自然嵌套成右结合。如果这里也用循环写成 `left = fastPow(left, right)` 迭代，就会变成左结合 `(2^3)^2 = 64`。

**为什么一元 `-` 要插在 `^` 之下、`*` 之上？** 因为：

* `-2^2` 应解释为 `-(2^2) = -4`，所以一元负号优先级必须**低于** `^`（否则 `^` 会先被 `parseUnary` 吃掉左边导致解析错误）。
* `-2*3` 应解释为 `(-2)*3`，一元负号优先级必须**高于** `*`。

`parseUnary → -parseUnary()` 的递归形式同时解决了**连续负号** `--5`（递归多次取反，天然正确）和**带括号负操作数** `-(-8)`（`parseUnary` 递归到 `parsePrimary` 处理括号）。

### 3. 括号的处理——递归入口与出口

`parsePrimary` 中遇到 `(`：

* **入口**：`pos++` 后**跳回最底层 `parseExpression`**。这是唯一合法的"下降到底层"的位置——括号内是一个全新独立表达式，优先级从头开始。
* **出口**：括号内表达式解析完后，**必须紧跟 `)`**，否则抛 `error`。这就是测试用例 `(2+8` 输出 `error` 的来源。

### 4. 错误检测的三种机制

**（a）结构性错误 → 抛 `CalcError(false)`**

* 需要原子时不是数字也不是 `(`（`parsePrimary` 开头）：覆盖 `(2+8`（缺右括号时，`parseExpression` 返回后 `parse` 里发现 `pos != size`）、`2+8)`（`)` 后还有内容，收尾检查命中）、`(2+8)(3+2)`（`parsePrimary` 拿到 `(2+8)` 后 `parseTerm`/`parseExpression` 的 while 看到 `(` 既不是 `* / %` 也不是 `+ -` 就退出，最终**顶层 `parse()` 发现 `pos != size`** 抛错）。
* 缺右括号：`parsePrimary` 中显式 `if (s[pos] != ')') throw`。
* **`(2)3(8)` 这类隐式乘法**：`2` 后 `3`，最外层收尾检查 `pos != size` → `error`。本算法**不支持隐式乘法**，正是靠"收尾必须消耗完整字符串"这一条兜住。

**（b）除零 / 模零 → 抛 `CalcError(true)`**

* 在 `parseTerm` 里判 `rhs == 0`，分 `/` 和 `%` 两种情况。
* 特别地 `8/(8+5-13)` 中 `8+5-13 = 0`，是在**求值时**才暴露除零，所以必须在运算现场判，而不能在词法阶段判。

**（c）幂运算的负指数 → 抛 `CalcError(false)`**

* `2^(2-5)` 指数算出 `-3`，`fastPow` 对负数指数无意义（且整数结果不能保留小数），按题意输出 `error`。

### 5. 优先级冲突的两个"陷阱"用例

* **`10-80-30)/3*3+4`**：`-80-30` 后面出现多余的 `)` → 在 `parseExpression` 的 while 里，`30` 之后 `parseTerm` 结束遇到 `)`，`parseExpression` 也结束，回到外层……最终顶层收尾 `pos != size` 发现 `)` 未消费 → `error`。
* **`30(/3+3)+4`**：`(` 内紧跟 `/`，`parsePrimary` 期望数字或 `(`，直接抛 `error`。

### 6. 数值与溢出

* 全部用 `long long`，题目给的规模下足够。
* `fastPow` 用**快速幂**（二进制展开），避免 `^` 暴力循环在指数较大时超时；同时指数为负在第一层 `parsePower` 就拦截了，`fastPow` 内部只处理非负整数。
* 题面"中间结果只保留整数"——除法和取模直接 C++ 整型语义（向零截断），与样例 `18/4=4`、`(2*3)/(5*2)=0` 吻合。

### 7. 与"算符优先算法"的对照

| **算符优先**        | **本实现**                               |
| --------------- | ------------------------------------- |
| `optr` 栈        | 函数调用栈（隐式）                             |
| 优先级表            | 函数调用链顺序                               |
| `#` 起止符         | `pos==size` 检查                        |
| 括号：`(` 入栈直到 `)` | `parsePrimary` 递归调用 `parseExpression` |
| 出错时栈/括号不匹配      | 异常抛出                                  |

如果严格按算符优先实现，需要维护 `optr` / `opnd` 两个栈并对比 `isp/icp` 表，代码量接近但不易处理"一元负号"和"幂右结合"——递归下降在这两点上表达力更强，所以本实现选择了它。

## 二、语法实现

### 1. 类封装与状态

```cpp
class Parser {
    string s;   // 表达式原文
    int pos;    // 当前扫描位置
```

把 `s` 和 `pos` 作为**成员状态**，所有 `parseXXX()` 成员函数共享同一个游标 `pos`，天然对应算符优先算法里"一个全局输入指针向前推进"的语义。相比把 `pos` 作为引用参数层层传递，成员变量写法更简洁。

### 2. 分层的函数签名

所有解析函数返回 `long long`（结果），无参——**输入靠成员 `pos` 推进，输出靠返回值**。这让函数之间可以互相 `parseXXX()` 调用，且每个函数只负责"我这一段优先级能产生的结果"。

```
long long parseExpression();  // 加减
long long parseTerm();        // 乘除模
long long parseUnary();       // 一元负号
long long parsePower();       // 幂
long long parsePrimary();     // 数字 / 括号
```

函数声明顺序**故意倒置**（先写 `Primary`，后写 `Expression`），因为 `Primary` 里要调用 `parseExpression` 处理括号，而 `parseExpression` 又要调用 `parseTerm`……在类体内所有成员函数都可互相调用，声明顺序不影响（类定义是"类作用域可见"），但**定义顺序**在类外实现时就必须按依赖拓扑排列——本实现把定义放在类内，用成员可见性绕过了前向声明问题。

### 3. `skip()` —— 空白吞噬

```cpp
void skip() {
    while (pos < s.size() && isspace(s[pos])) pos++;
}
```

每个需要"看下一个 token"的地方**先 skip**（`parsePrimary` 开头、`parseUnary` 开头、`parseTerm`/`parseExpression` 的 while 里、`parse()` 收尾前）。这样 `10 + -8` 里的空格被透明处理，同时**保证每个函数返回时 `pos` 停在非空白处**，上层 while 判断 `s[pos]` 时才准确。这是"游标式词法 + 语法合一"实现的必要条件。

### 4. 数字解析

```cpp
long long parseNumber() {
    if (!isdigit(s[pos])) throw CalcError(false);
    long long val = 0;
    while (isdigit(s[pos])) val = val * 10 + (s[pos++] - '0');
}
```

一次性读完整段连续数字，**遇到非数字立即停**，不跨越运算符边界。`-` 号由上层 `parseUnary` 处理，所以 `parseNumber` **从不处理负号**——负号的处理位置严格由优先级层级决定，非常干净。

### 5. 异常作为控制流

```cpp
struct CalcError {
    bool divide0;
    CalcError(bool d = false) : divide0(d) {}
};
```

用一个**带标记的单一异常类型**表示两类错误，避免定义两个异常类。`divide0 == true` → `Divide 0`，否则 `error`。抛出点：

* `parsePrimary`：非法原子、缺 `)`
* `parsePower`：负指数
* `parseTerm`：除零 / 模零
* `parse()`：多余的尾部字符

捕获点在 `main` 的 `try/catch`，**一处捕获，根据 `e.divide0` 分两路输出**。这种设计让每个解析函数的错误路径极短（一行 `throw`），主逻辑保持线性可读。

### 6. 关键算法细节实现

**快速幂**：

```cpp
long long fastPow(long long base, long long exp) {
    long long res = 1;
    while (exp > 0) {
        if (exp & 1) res *= base;
        base *= base;
        exp >>= 1;
    }
    return res;
}
```

标准二进制快速幂，`O(log exp)`。注意 `exp` 在这里已由 `parsePower` 保证非负，函数内无需再判负数。

**幂右结合**：

```cpp
if (s[pos] == '^') {
    pos++;
    long long right = parseUnary();   // 注意：递归 parseUnary，不是循环
    if (right < 0) throw CalcError(false);
    return fastPow(left, right);
}
```

这里**只有 `if` 没有 `while`**——处理一个 `^` 后立即返回，右边的 `^` 由 `right = parseUnary()` 递归中继续处理，形成 `((2^3^2) → 2^(3^2))` 的右嵌套结构。这正是与 `parseTerm` 左结合 `while` 的关键区别。

**为什么 `parsePower` 里要先判负指数再算**：因为 `fastPow` 遇到负 `exp` 时 `while(exp>0)` 一次不进，直接返回 `1`，结果错误（如 `2^-3` 会得 `1`）。所以必须在调用前检查并抛错。

### 7. 输入输出

```cpp
cin >> N;
cin.ignore(numeric_limits<streamsize>::max(), '\n');
```

`getline` 前必须吃掉 `cin >> N` 留下的换行，否则第一次 `getline` 读到空串——这是**混合使用 `>>` 和 `getline` 的经典陷阱**。用 `numeric_limits<streamsize>::max()` 而不是固定数字，避免缓冲区超长被截断。

```cpp
ios::sync_with_stdio(false);
cin.tie(nullptr);
```

关闭 C 与 C++ 同步、解绑 `cin/cout`，加速 I/O——本题可能表达式很多，这个小优化有时是"过/不过"的分水岭。

### 8. 递归深度与栈安全

递归深度 = 表达式嵌套深度 + 运算符数量（因为 `parseExpression → parseTerm → parseUnary → parsePower → parsePrimary` 每条链最多 5 层，但在 `parseExpression` 的 `while` 里每次只调 `parseTerm`，不递归到自身；真正的递归深度来自 `(` 嵌套和 `^` 链、一元负号链）。对一般题目规模（几百字符）完全安全，无需手动栈。

### 9. 一个值得注意的隐含约定

`parsePrimary` 遇到 `(` 时**直接调用 `parseExpression`（最低优先级）**，而不是 `parseTerm` 或更高级——这是括号语义的体现：**括号内的一切优先级重新从最低开始**。如果错误地调 `parseTerm`，`(2+3)*4` 就会解析失败。

***

## 总结

* **算法上**：递归下降 = 算符优先的"函数化"版本，把优先级表编码为函数调用层次，把左/右结合编码为 `while`/递归 的选择，把括号编码为"降到最低层函数"的跳转，把 `#` 起止符编码为顶层收尾检查。
* **语法上**：类封装统一游标；异常机制统一错误出口；`skip` 保证函数间游标契约；快速幂 + 显式负指数检查 + 右递归处理 `^`；`>>` 与 `getline` 混用的缓冲清理；I/O 解绑。

# 核心逻辑 · 数据结构 · 算法 三视角拆解

***

## 一、问题的抽象与核心逻辑

### 1.1 三个子问题合一

表面看是"求值"，实际是**三件事同步完成**：

| **层次** | **问题**      | **失败表现**                      |
| ------ | ----------- | ----------------------------- |
| 语法     | 字符串是否是合法表达式 | `error`（括号不配对、隐式乘法、缺操作数）      |
| 语义     | 运算是否可执行     | `Divide 0`（除/模零）、`error`（负指数） |
| 求值     | 算出整数结果      | 正常数值                          |

**关键判断**：能否把三者合成**单遍扫描**？可以——因为不需要语法树，扫描到哪儿算到哪儿。这决定了整个设计的总基调：**游标推进 + 边走边算 + 出错即抛**。

### 1.2 核心逻辑链条

```
字符串 → 游标从左到右推进 → 每遇到一个运算符，按优先级决定"现在算还是等"
       → 结果通过函数返回值向上汇聚 → 顶层检查游标是否走完 → 输出三态
```

这条链里**唯一的状态是游标**，"运算该不该现在做"由**函数调用层次**隐式决定——这是全文最核心的思想，后面所有设计都是它的展开。

***

## 二、数据结构选择

### 2.1 唯一显式数据结构：`(字符串, 游标)`

```
s: 表达式原文
pos: 当前扫描位置（唯一可变状态）
```

这对应算符优先算法里"输入指针"的角色。**没有 AST、没有符号表、没有显式栈**——因为单遍求值不需要它们。

**为什么省掉 AST？** 建树要两遍（建树 + 求值），还要分配节点；单遍求值一遍搞定，且错误能在**发现的瞬间**定位（见 3.5）。对本题"输出三态"的需求，单遍更直接。

### 2.2 隐式数据结构：函数调用栈 = 优先级表

这是本设计**最精巧的替代**：算符优先算法需要一张显式的 `isp/icp` 优先级表 + 一个算符栈，递归下降把二者都消掉了：

* **优先级表** → 编码成"函数调用的层次顺序"（低优先级函数在栈底，高优先级在栈顶）
* **算符栈** → 就是**函数调用栈本身**（运行时自动维护）

于是"栈顶算符 vs 当前算符"的比较，变成了"当前函数该不该调用下层函数"的选择——**比较动作消失，只剩调用动作**。

### 2.3 错误载体：带标记的异常

输出三态（数值 / error / Divide 0）不能用返回值表达——**返回值域被 `long long` 占满**（负数、0 都是合法结果）。所以需要一条**旁路通道**：

```
struct CalcError { bool divide0; }
```

* 沿函数调用栈**向上传播**（栈展开天然对应"错误回溯"）
* 顶层唯一捕获点按 `divide0` 分流输出

这种"值走返回值，错误走异常"的**双通道**设计，让每个解析函数的主逻辑保持线性、无错误分支污染，这是它能替代算符优先"栈内不匹配检测"的关键。

### 2.4 数值域：`long long`

幂运算极易溢出，且指数可能不小；`int` 不够，`long long` 是低成本的稳妥选择。除法/取模用 C++ 整型语义（向零截断），与题面"中间结果保留整数"一致。

***

## 三、算法设计

### 3.1 优先级分层：五层函数链

算法把运算符按优先级从低到高**切成五段**，每段一个函数，函数调用方向 = 优先级升高方向：

```
parseExpression   + -           （最低）
  └ parseTerm     * / %
    └ parseUnary  一元 -
      └ parsePower ^
        └ parsePrimary  数字 / ( 表达式 )   （最高）
```

**为什么这样分层就能保证"先乘除后加减"？**&#x4F4E;优先级函数在解析完自己的一段后，**向右递归调用更高优先级函数**去取右操作数。高优先级函数只在自己那层消耗运算符，不越界。于是 `10-20/4` 中 `-` 后面的 `20/4` 作为一个整体返回——乘除自然先算，**无需优先级比较**。

### 3.2 结合性：循环 vs 递归的分界（算法核心）

这是整个程序**最具算法含量的设计决策**：

| **运算**      | **结合性** | **实现**           | **语义**            |
| ----------- | ------- | ---------------- | ----------------- |
| `+ - * / %` | 左       | **`while` 循环累积** | `a-b-c = (a-b)-c` |
| `^`         | **右**   | **递归自身**         | `a^b^c = a^(b^c)` |
| 一元 `-`      | 右（前缀）   | 递归自身             | `- -a`            |

**为什么左结合用循环？**`v = v op parseHigher()`，每轮右边只调更高优先级，结果**立即扣回 v**。`10-20/4`：`v=10`，循环里 `v -= parseTerm()`，`parseTerm` 返回 `5`，`v=5`。左结合自然产生。

**为什么右结合必须递归？**&#x5E42;的关键是"右边的指数本身可能还是一整个幂表达式"。若用循环写 `left = pow(left, right)` 迭代，会变成 `(2^3)^2 = 64`；用递归让"右边再次进入同一层解析"，就得到 `2^(3^2) = 512`。**同一层函数递归自身 = 右结合**，这是递归下降里结合性的通用编码规则。

**一元 `-` 插在 `^` 与 `*` 之间的理由**：

* `-2^2` 应为 `-(2^2)=-4` → 一元负号优先级必须**低于 `^`**（让 `^` 先结合）
* `-2*3` 应为 `(-2)*3` → 一元负号优先级必须**高于 `*`**
* `- -8`（连续负号）→ 递归自身天然处理
* `10 + -8`（负操作数）→ 负号在 `parseUnary` 被吃掉，`parsePrimary` 只认数字，无歧义

这一层的插入位置**恰好卡在两处优先级之间**，是分层链唯一的正确解。

### 3.3 括号：优先级"归零"跳转

括号的语义是"内部一切重新从最低优先级算起"。算法用**递归调用最低层函数**实现：

```
遇到 '(' → pos++ → 调用 parseExpression（最低层！）
```

**为什么必须调到最低层？** `(2+3)*4` 里括号内有加减，若错调 `parseTerm` 就解析不了 `+`。**"调用最低层"= 优先级归零**，这是括号语义在递归下降里的精确编码。

出口：括号内解析完后**必须紧跟 `)`**，否则抛 `error`——这就是 `(2+8` 输出 `error` 的来源。

### 3.4 幂运算的两个算法点

**（1）快速幂：`O(log e)`**&#x6307;数可能较大，暴力循环会超时。二进制快速幂把 `e` 按位展开，每次底数平方、指数右移。这是本题唯一需要独立算法的子过程。

**（2）负指数必须在调用前拦截**快速幂对 `exp < 0` 无定义（`while(exp>0)` 一次不进返回 1，结果错误）。所以 `parsePower` 里**先判 `right < 0` 抛 `error`，再调用快速幂**。这是"算法前置条件必须显式检查"的典型例子——样例 `2^(2-5)` 输出 `error` 靠的就是这一行。

### 3.5 错误检测：三种机制覆盖全部失败模式

| **机制**       | **触发点**                                    | **覆盖场景**                                          |
| ------------ | ------------------------------------------ | ------------------------------------------------- |
| **异常（结构错误）** | 原子位置既非数字也非 `(`、括号内缺 `)`、顶层收尾 `pos != size` | `(2+8`、`2+8)`、`(2+8)(3+2)`、`(2)3(8)`、`10(20-8)+2` |
| **异常（除零标记）** | 除法/取模前 `rhs == 0`                          | `8/0`、`8/(8+5-13)`、`10/0`                         |
| **异常（负指数）**  | `parsePower` 中 `right < 0`                 | `2^(2-5)`                                         |

**关键洞察：三态输出的本质是"错误分类"，不是"错误有无"。** 单一异常类型 + 一个 `bool divide0` 标记，一处捕获分流，比两个异常类更省。

**顶层收尾检查 `pos == size` 是通用兜底**：`(2)3(8)`、`(2+8)(3+2)` 这类"隐式乘法"（题目不支持）在解析过程中**不会报错**——`(2)` 作为原子返回后，`parseTerm`/`parseExpression` 看到下一个字符是 `(` 而非 `* / % + -`，while 退出，函数正常返回。**只有顶层发现游标没走完**才判定非法。这说明：**"解析成功" ≠ "整句合法"**，收尾检查是必要且唯一能兜住这类错误的地方。

### 3.6 幂等的 `fastPow` 为何是 `long long` 参数

指数用 `long long`，避免 `parsePower` 传入的 `right` 在 `int`/`long long` 间强转溢出——虽然本题规模用不到，但签名一致能防"负数被截断成非负"的隐蔽 bug。

## 四、与算符优先算法的对照（题面要求）

| **维度**  | **算符优先**       | **本程序（递归下降）**       |
| ------- | -------------- | ------------------- |
| 优先级     | 显式 `isp/icp` 表 | **函数调用层次**隐式编码      |
| 算符存储    | 显式 `optr` 栈    | **函数调用栈本身**         |
| 操作数存储   | 显式 `opnd` 栈    | **函数返回值**           |
| 括号      | `(` 入栈直到 `)`   | 递归调最低层函数            |
| 结合性     | 优先级表里带 `=` 号   | 左→`while`，右→递归自身    |
| 起止符 `#` | 显式             | 顶层 `pos == size` 检查 |
| 错误定位    | 栈不匹配时回溯        | **抛出点即定位点**         |
| 一元负号    | 需额外规则          | 独立层级天然处理            |

**等价的本质**：算符优先和递归下降都在编码同一张优先级表，只是一个用数据（表 + 栈），一个用控制流（函数链 + 调用栈）。**递归下降的栈是运行时自动维护的**，代码更短，但对"一元负号""幂右结合"这类规则性强的运算符表达力更强——这是本实现选择它的原因。

## 五、正确性与复杂度

### 5.1 正确性论证（归纳法）

对任意合法表达式 `E`，设其按优先级最外层运算符切分为 `E = A op B`：

* **归纳假设**：`parseExpression/parseTerm/...` 能正确解析并求值任意更低优先级的子表达式
* **归纳步骤**：
  * `op` 在 `+ -` 层 → 由 `parseExpression` 处理，左子式已求值于 `v`，右子式经 `parseTerm` 递归求值
  * `op` 在 `* / %` 层 → `parseTerm` 同理
  * `op` 是 `^` → `parsePower` 递归取右
  * `op` 是一元 `-` → `parseUnary` 递归取右
  * 原子 → `parsePrimary` 处理数字或括号（括号内递归到最低层）
* 层层归纳覆盖所有表达式，**顶层收尾检查**保证无残留字符。

### 5.2 复杂度

* **时间**：除幂运算外**单遍扫描** `O(n)`；幂运算内部 `O(log e)`，最坏 `O(n · log e_max)`。快速幂避免了 `O(e)` 的暴力指数循环。
* **空间**：无显式栈/树，**只有递归深度** `O(d)`，`d ≤ 表达式嵌套深度 + 一元负号链长 + 幂链长`，题面规模（几百字符）完全安全。

## 六、设计权衡总览

| **决策点** | **选择**            | **放弃的方案**  | **理由**                   |
| ------- | ----------------- | ---------- | ------------------------ |
| 语法/求值   | **单遍合并**          | 建 AST 再求值  | 不建树省内存，错误即抛即定位           |
| 优先级     | **函数分层**          | 显式优先级表     | 表 + 栈自动消除，代码更短           |
| 结合性     | 左循环 / 右递归         | 统一用栈 + 标志位 | 语义清晰，无状态位                |
| 错误载体    | **异常 + 标记**       | 返回值/错误码    | 值域被 `long long` 占满，需旁路通道 |
| 错误分类    | **单一异常 + bool**   | 两个异常类      | 一处捕获，分流输出                |
| 隐式乘法    | **不支持**（收尾检查兜底）   | 词法阶段禁止相邻原子 | 只靠一条顶层检查覆盖全部用例           |
| 幂运算     | **快速幂 + 显式负指数检查** | 暴力循环 / 不检查 | 防超时，负指数前置拦截              |

**一句话总结**：这个程序把"表达式求值 + 合法性判定 + 错误分类"三件事压缩成**单遍游标扫描 + 五层函数递归**，用**函数调用栈替掉算符栈**、用**异常旁路替掉错误码**、用**循环/递归分界编码结合性**、用**顶层收尾检查兜底隐式乘法**——每一处设计都是对算符优先算法的"数据结构 → 控制流"等价替换，最终得到一个更短、错误定位更直接、对一元负号与幂右结合表达更自然的实现。
