## 3. 它们怎么配合？

阅读顺序建议（从顶层往下）：

```
先读《文档地图与缺口清单》（本文档的"总目录"）
  ↓
再读《人类 README》（就是本文件，讲进度）
  ↓
需要执行时 → 把《AI 交接 README》给 AI agent
  ↓
AI 按批次读 数据契约 → 剧本对应章节 → 写 story_config.js
```

数据流向：**剧本（内容） → 方案（裁定） → 采纳基线（拍板） → 数据契约（落码规格） → 游戏代码**。规则冲突时以"项目方最新裁定 > 数据契约 > 方案 > 剧本"为准。

## 6. 常见问题

**Q：这些文档会不会改来改去？**
A：源文档（剧本/方案）原则上冻结；交付文档（基线、契约）会随着决策回填而更新，每次更新建议改文件名日期后缀，避免覆盖历史。

**Q：AI 拿到文档就能干活吗？**
A：可以。K/M、D/N/F/E 与第零线的数据契约均已定稿、口径已闭合，落码后用三层校验 + 回归清单自证；推荐顺序按批次 1（K/M）→ 2（D/N/F）→ 3（X4 告别 + E）→ 5（第零线，可选）。

**Q：改动游戏代码有风险吗？**
A：有硬性保护——四协议解锁逻辑（inherit/public_energy/charter 的 requirements）不允许任何扩展线写入；事件类型白名单也已写明。落码后靠三层替代校验规范（G5，已定案）+ 回归测试兜底。
