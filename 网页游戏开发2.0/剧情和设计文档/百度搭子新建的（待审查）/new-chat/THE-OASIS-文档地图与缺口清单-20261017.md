## 2. 文档间的逻辑关系与使用顺序

### 2.1 数据流（谁决定谁）

```
SCREENPLAY（内容事实源）
   │ 6.0-6.6b 七条扩展线节拍+全文
   ▼
PROPOSAL（第零线方案裁定，S3）─── 只对第零线/第六协议做补丁
   │ 4.1-4.4 定线/入口/Z节拍/结局正文
   ▼
BASELINE（D1）─── 项目方"采纳了什么、红线是什么"
   ▼
数据契约（G1-G4 已定稿 ✅）─── 落码唯一规格，自包含
   │ 事件类型白名单 / flag+clue 清单 / 双语对白 / 演出预算
   ▼
story_config.js（唯一改动面）─── i18n.js（双语）─── store.js（存档）
   │
   ▼
三层替代校验规范（G5 已定案）─── 回归测试（G6 已补齐：《THE-OASIS-回归测试清单-20261018.md》）
```

### 2.2 权威性排序（冲突时以谁为准）

```
项目方/用户裁定 ＞ 数据契约（BASELINE 采纳范围内）＞ PROPOSAL ＞ SCREENPLAY ＞ 工程现状
```

数据契约描述与剧本正文冲突时（如 KM 契约记录的 M 线演出数量矛盾，见 D2 第三部分 L210），已由项目方按 **2 段口径** 定案并回填；后续再遇同类矛盾，以契约标注口径执行，同时滞留待决策项回填，不能默默吞掉。

### 2.3 给 AI 的消费顺序（按落码批次）

1. 读 `BASELINE`（红线：不触碰四协议解锁布尔、事件白名单、filter 只收 flag）；
2. 读要落码批次的 `数据契约`（KM / ZERO / D/N/F/E，四线契约已定稿）；
3. 按契约锚点回 SCREENPLAY/剧本 对应节（2.4 K 线、7.3 M 线、6.2b-6.6b 各线全文、PROPOSAL 4.3 Z 节拍）核对上下文；
4. 在 `story_config.js` 落码 → 同步 `i18n.js` 双语 → 确认 store 兼容（PROGRESS_VERSION）；
5. 跑三层替代校验（G5）→ 回归冒烟。

### 2.4 写入位置映射（落码总规则）

| 内容类型 | 写入位置 |
|---------|---------|
| 对话（中/英） | story_config 的 dialogueTree + dialogueTree_en（两处同步） |
| 剧情 flag | store 的 story.flags[]（filter/ifFlag 判定） |
| 线索 clue | store 的 story.clues[]（**必须走 ifClue 判定，不能进 filter**） |
| 事件序列 | 仅可用白名单事件（见附录 A） |
| 结局/reviews | 四协议解锁布尔派生状态零改动（inherit/public_energy/charter 的 requirements 不可写） |

### 4.5 口径 G5 · verify-config 校验方式（已定案：三层替代校验规范）

【原占位】《THE-OASIS-verify-config校验说明-YYYYMMDD.md》或由项目方提供工具。

经工程核实：`oasis-game-draft/` 内**不存在 verify-config 脚本实体**，`index.html` 仅保留加载期守卫注释（verify-boot ⑩ / verify-lint ③⑤ / verify-boot ⑩A 的脚本加载顺序三元组守卫）。为不阻塞 K/M 与第零线落码后的自证，依据工程实际定案为**三层替代校验规范**；若日后项目方提供真实工具，优先用工具并以其通过条件为准。

- **第 1 层 · 静态一致性检查**（落码后、提交前）：
  - 事件类型全量在白名单内（附录 A，可脚本 grep 核对）；
  - 新增 flag/clue 均有引用闭环：定义处（setFlag/discoverClue）与判定处（ifFlag/ifClue）一一对应，无孤立引用；
  - 双语成对：`dialogueTree` 与 `dialogueTree_en` 每个新增键成对出现，key 集合 diff 为空；
  - 四协议 requirements diff 为零：inherit / public_energy / charter 各层 `requirements` 全量比对落码前后无变化；
